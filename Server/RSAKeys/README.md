# Server-Side Cryptographic Key Storage

This directory manages the RSA key pairs and public certificates required for client identity verification, transport-layer security, and the distribution of end-to-end encryption (E2EE) peer keys.

---

| Folder | Key Type | Persistence | Primary Purpose |
| --- | --- | --- | --- |
| **`ClientRegisteredPublicKeys/`** | Public Key (RSA-4096) | Persistent | Account authentication and E2EE peer-to-key distribution. |
| **`ClientTempPublicKeys/`** | Public Key (RSA-4096) | Ephemeral (Per-session) | Transport-layer hybrid encryption (AES/RSA) tunneling. |
| **`ServerPermanentKeys/`** | Key Pair (RSA-4096) | Persistent | Server root of trust, inbound decryption, and outbound signing. |

---

**Directory Specifications**

* **`ClientRegisteredPublicKeys/` (Permanent Client Identity Keys)**
* Persists the authoritative public keys of all registered users on the server.
* Utilized strictly for validating account login signatures and distributed dynamically to other clients upon request to facilitate peer-to-peer E2EE chat sessions. The server never possesses the corresponding private keys.


* **`ClientTempPublicKeys/` (Session Ephemeral Keys)**
* Caches the temporary public keys generated by clients during the initial handshake to secure the client-server transport boundary.
* Used by the server to encrypt outbound AES-256 session keys and verify inbound packet signatures for active sockets.
* **Volatile Storage:** Keys in this directory are aggressively purged immediately upon client disconnection, socket timeout, or graceful server shutdown to ensure forward secrecy.


* **`ServerPermanentKeys/` (Root of Trust)**
* Contains the server's master RSA-4096 key pair used to decrypt incoming client payloads and digitally sign all outbound server responses.
* **CRITICAL OPERATIONAL HAZARD:** The server's public key certificate is directly tied to a hardcoded SHA-512 fingerprint embedded inside the client application. If this key pair is ever regenerated or altered, the `client.py` source code in the `Asset/` folder **must** be updated with the new hash and redistributed. Failure to do so will cause all clients to reject the server connection as a Man-in-the-Middle (MITM) attack.
